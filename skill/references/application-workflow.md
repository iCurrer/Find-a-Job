# 投递状态机与执行流程（application-workflow）

## 适用范围

- 本文件定义 `applications/applications.json` 的状态机、唯一写入口、提交证据、重复申请拦截与人工操作清单。
- 在以下时机加载：更新投递状态之前；登记提交结果/证据之前；判断能否重试或重复投递之前；需要向用户输出人工操作清单之前。
- 唯一写入口是 `scripts/update_application.py`；**禁止**直接编辑 `applications.json`，禁止绕过状态机。

## 1. 状态与含义

| 状态 | 含义 |
| --- | --- |
| `待准备` | 岗位值得申请，材料尚未就绪 |
| `待确认` | 申请内容已准备好，等待用户审核、修改或批准 |
| `执行中` | 用户已授权，正在填写/上传/校验 |
| `已提交` | 已有可验证证据证明提交完成 |
| `需人工介入` | 验证码、登录失效、页面变化或信息冲突，暂停并请求用户处理 |
| `失败` | 本次操作未完成，记录原因，修复后可重试 |
| `已关闭` | 不再跟进，保留历史记录 |
| `笔试` | 已进入笔试环节 |
| `面试` | 已进入面试环节 |
| `拒绝` | 收到拒绝结果 |
| `Offer` | 收到录用通知 |

所有状态都保留在 `history[]` 中，不删除历史记录。

## 2. 完整迁移表

只允许以下迁移；未列出的迁移一律拒绝（退出码 `1`）：

| 当前状态 | 允许迁移到 | 说明 |
| --- | --- | --- |
| `待准备` | `待确认`、`已关闭` | 材料就绪→待确认；放弃→已关闭 |
| `待确认` | `执行中`、`待准备`、`已关闭` | 用户批准→执行中；需修改→退回待准备；取消→已关闭 |
| `执行中` | `已提交`、`需人工介入`、`失败` | 有证据→已提交；遇验证码/登录失效/页面变化→需人工介入；本次未完成→失败 |
| `需人工介入` | `执行中`、`失败`、`已关闭` | 用户处理完毕→执行中；无法继续→失败；放弃→已关闭 |
| `失败` | `执行中`、`已关闭` | 修复后重试→执行中；放弃→已关闭 |
| `已提交` | `笔试`、`面试`、`拒绝`、`Offer`、`已关闭` | 按进程与结果迁移 |
| `笔试` | `面试`、`拒绝`、`已关闭` | 按进程与结果迁移 |
| `面试` | `Offer`、`拒绝`、`已关闭` | 按进程与结果迁移 |

契约原文形式（便于逐条核对，与上表等价）：

```
待准备 -> 待确认 | 已关闭
待确认 -> 执行中 | 待准备 | 已关闭
执行中 -> 已提交 | 需人工介入 | 失败
需人工介入 -> 执行中 | 失败 | 已关闭
失败 -> 执行中 | 已关闭
已提交 -> 笔试 | 面试 | 拒绝 | Offer | 已关闭
笔试   -> 面试 | 拒绝 | 已关闭
面试   -> Offer | 拒绝 | 已关闭
```

补充规则：

- `已关闭` 为终态，不再迁出。
- 状态只能前进或按表中允许的方式回退；不得跳级（如 `待准备` 直接到 `已提交`）。
- 每条迁移都写入 `history[]`（时间、from、to、note），并由脚本追加 JSONL 审计日志。

## 3. 唯一写入口与命令

```bash
# 建立或推进到待准备
python scripts/update_application.py --job-id job-6d4169afd8-bb41 --status 待准备 \
  --notes "用户已选定该岗位，材料准备中"

# 材料就绪，进入待确认（等待用户批准）
python scripts/update_application.py --job-id job-6d4169afd8-bb41 --status 待确认 \
  --notes "简历 v1.0 与求职信 v1.0 已生成"

# 用户批准后进入执行中
python scripts/update_application.py --job-id job-6d4169afd8-bb41 --status 执行中 \
  --notes "用户于 2026-10-29 12:30 明确批准执行"

# 拿到可验证结果后登记已提交（evidence 必填）
python scripts/update_application.py --job-id job-6d4169afd8-bb41 --status 已提交 \
  --evidence "示例平台确认页，申请编号 APP-EXAMPLE-0001；用户已保存截图"

# 遇到验证码/登录失效
python scripts/update_application.py --job-id job-6d4169afd8-bb41 --status 需人工介入 \
  --notes "出现验证码，已暂停，等待用户处理"
```

- 输出契约：`{ok, application_id, status, history_count, backup}`。
- 退出码：`0` 成功；`1` 业务规则失败（非法迁移、重复申请、证据缺失）；`2` 参数或文件缺失（如缺少 `--job-id` / `--status`，或指定路径不可读）。记录文件不存在时按空记录初始化，首次创建固定为 `待准备`。
- 写前自动生成 `applications.json.bak`，并追加 JSONL 审计日志（不记敏感信息）。
- `application_id` 格式为 `app-YYYYMMDD-NNNN`，例如 `app-20261029-0001`，由脚本生成，不由文档手写。
- 同一次运行内串行更新状态，不并发写同一个记录文件。

## 4. 确认点规则

外部写入（真实投递、发送邮件、上传个人资料、提交声明）必须经过显式确认：

1. `待准备 → 待确认`：材料就绪后展示完整内容与待确认项。
2. `待确认 → 执行中`：需要用户**明确批准**（例如「确认提交」「批准执行」），含糊表述（「看起来还行」）不构成批准。
3. 确认前展示：公司、岗位、地点、材料版本、网申关键答案、将要执行的动作、目标平台。
4. 确认内容写入 `notes` 并追加审计日志（记录时间与确认摘要，不记录敏感信息）。
5. 一次确认只覆盖一次具体动作；不因上次确认而自动批量投递其他岗位。

## 5. 已提交证据要求

- `--evidence` 必须非空，否则脚本拒绝（退出码 `1`），状态保持原值。
- 可用证据形式：平台确认页 URL、确认邮件主题与时间、申请编号、用户保存的截图文件路径（相对路径）与说明。
- `submitted_at` 由脚本在进入 `已提交` 时自动写入，不由文档手填。
- **只有「已填写」「已点击提交」不算已提交**；必须存在平台侧可验证的接收结果。
- 证据不得包含密码、Cookie、令牌、验证码；截图由用户自行保存，记录中只登记可识别的文件名或链接。
- 不得伪造证据；无法取得证据时保持 `需人工介入` 或 `失败`，并请用户核对。

## 6. 重复申请拦截

- 同一 `job_id` 已存在 `已提交` / `笔试` / `面试` / `Offer` 记录时，再次提交被**拒绝**（退出码 `1`，重复申请风险）。
- 重试前必须检查：当前状态、`submitted_at`、`submission_evidence`、`history[]`，确认没有已发生的提交。
- 状态为 `失败` / `需人工介入` 时重试，先核对平台侧是否已收到申请；无法确认则先问用户。
- 状态为 `已关闭` 的历史记录不触发自动拦截，但报告中必须提示「该岗位曾投递并关闭」，由用户决定是否重新申请。
- 不得通过手工编辑 JSON、删除记录或新建重复 `job_id` 绕过拦截。

## 7. 无执行器时的人工操作清单

当浏览器/手机执行器未接入（P0 未验证）时，输出**可复制**的人工操作清单，不输出「已投递」结论：

```markdown
## 人工操作清单 — job-6d4169afd8-bb41（示例科技 / 后端开发实习生）

- [ ] 打开来源链接：https://example.com/jobs/12345（示例）
- [ ] 上传简历：resumes/job-6d4169afd8-bb41/resume-job-6d4169afd8-bb41-v1.0.pdf
- [ ] 上传求职信：resumes/job-6d4169afd8-bb41/cover-letter-job-6d4169afd8-bb41-v1.0.pdf
- [ ] 按材料填写网申问题（答案见 resume-job-6d4169afd8-bb41-v1.0.md 附注）
- [ ] 提交前核对：公司/岗位/地点/联系方式/材料版本
- [ ] 提交后记录证据（确认页链接或申请编号）
- [ ] 回填状态：
      python scripts/update_application.py --job-id job-6d4169afd8-bb41 --status 已提交 --evidence "<确认页链接或申请编号>"
```

- 清单必须包含目标岗位、材料路径、提交前核对项、证据回填命令。
- 用户完成并回填前，状态保持 `待确认` 或 `执行中`（如用户已开始操作），不擅自改为 `已提交`。

## 8. 记录字段与示例

```json
{
  "application_id": "app-20261029-0001",
  "job_id": "job-6d4169afd8-bb41",
  "company": "示例科技",
  "title": "后端开发实习生",
  "status": "待确认",
  "resume_version": "resume-job-6d4169afd8-bb41-v1.0",
  "cover_letter_version": "cover-letter-job-6d4169afd8-bb41-v1.0",
  "prepared_at": "2026-10-29T12:20:00+08:00",
  "submitted_at": "",
  "submission_evidence": "",
  "next_action": "等待用户确认后执行投递",
  "follow_up_at": "2026-10-31T10:00:00+08:00",
  "notes": "用户已选定该岗位",
  "outcome": "",
  "history": [
    {"at": "2026-10-29T12:20:00+08:00", "from": "", "to": "待准备", "note": "创建记录"},
    {"at": "2026-10-29T12:25:00+08:00", "from": "待准备", "to": "待确认", "note": "材料版本 v1.0 已生成"}
  ]
}
```

- 记录顶层含 `schema_version`、`updated_at`；时间统一 ISO 8601 带时区。
- `next_action` 与 `follow_up_at` 每次状态变化后更新，作为跟进提醒依据。

## 9. 备份、审计与恢复

- 每次 `update_application.py` 写入前生成 `applications.json.bak`（上一次内容），再追加 JSONL 审计日志到 `logs/`。
- 审计日志字段：时间、任务、`application_id`、`job_id`、from/to 状态、结果摘要；不记录密码、Cookie、验证码或不必要的个人信息。
- 恢复步骤：停止写入 → 对比当前文件与 `.bak` 差异 → 经用户确认 → 用 `.bak` 覆盖 → 记录恢复原因与时间。
- 恢复后重新校验记录完整性（状态是否合法、history 是否连续）。

## 10. 失败处理

| 情形 | 退出码 | 处理 |
| --- | --- | --- |
| 非法状态迁移（不在迁移表） | `1` | 拒绝写入，展示当前状态与允许的下一步；状态不变 |
| 重复申请（同 `job_id` 已有 已提交/笔试/面试/Offer） | `1` | 拒绝并提示重复风险；由用户决定是否人工处理 |
| `--evidence` 为空却要求 `已提交` | `1` | 拒绝；先取得可验证证据 |
| `job_id` 不存在 / 参数缺失 / 记录文件缺失 | `2` | 核对参数与路径；不新建假记录 |
| 提交后无确认结果 | — | 不得标记 `已提交`；转 `需人工介入`，请用户核对 |
| 页面变化 / 验证码 / 登录失效 | — | 立即停止，转 `需人工介入`，不尝试绕过 |
| 写入中断 | `1`/`2` | 检查 `.bak` 与审计日志后恢复；恢复前确认无并发写入 |
| 用户拒绝已准备的申请 | — | 按迁移表退回 `待准备` 或 `已关闭`，记录原因 |
