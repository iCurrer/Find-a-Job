# 岗位搜索策略（job-search-policy）

> 适用时机：用户说「帮我找岗位」「搜一下有什么岗」「最近有什么新机会」时。
> 本文件定义**搜索这件事的边界**：谁去搜、怎么搜、什么不许做、结果怎么落盘。
> 与 `browser-policy.md`（执行器底层规则）配套阅读，冲突时以本文件对「搜索」的具体条款为准。

## 1. 三层结构

搜索不是一步，是三段，每段失败方式不同：

| 层 | 做什么 | 执行者 | 是否需要能力验证 |
| --- | --- | --- | --- |
| **L1 生成搜索计划** | 按 `config/search.json` 拼出各平台搜索链接 | `scripts/search_urls.py`（纯本地） | 不需要。不联网，随时可用 |
| **L2 只读抓取列表** | 打开搜索页，读岗位卡片，抽字段 | Agent（三条通道，见第 2 节） | 按通道区分，见第 2 节 |
| **L3 详情与导入** | 补全岗位字段，落 `jobs/raw/`，走 `normalize_jobs.py` | Agent + 既有脚本 | 不需要 |

**顺序不可颠倒**：先出计划、再抓取、再导入。不允许「边搜边投」，也不允许跳过 L1 直接凭记忆编岗位。

## 2. 三条执行通道

`browser-policy.md` 原来只有 A/B 两条路径，加入搜索后必须区分第三条 —— 因为它不需要浏览器能力验证，是当前**唯一能立刻跑通**的通道。

| 通道 | 手段 | 前置条件 | 能拿到什么 | 拿不到什么 |
| --- | --- | --- | --- | --- |
| **A 用户登录标签页** | `user_open_tabs` → `tabs_claim` → `dom_cua_get_visible_dom` | 用户已登录并在浏览器打开该页面；`browser_exec=verified` | 完整列表（含需登录才显示的内容） | — |
| **B 公开页只读** | `tabs_new` + `tab_goto` + `dom_cua_get_visible_dom` | `browser_exec=verified`；页面公开可访问 | JS 渲染后的完整列表 | 登录后才可见的岗位 |
| **C 文本只读** | `WebFetch` 抓页面文本 | **无**（不需要 `browser_exec` 验证） | 服务端渲染的列表（如实习僧、牛客） | JS 渲染的列表（如应届生求职网） |

**通道选择顺序**：C → B → A。先试代价最低的；C 拿不到再上浏览器。不要一上来就接管用户的标签页，那是打扰。

**各平台适用通道**（2026-10-29 实测，记录在 `config/search.json` 的 `fetch_mode`）：

| 平台 | 推荐通道 | 依据 |
| --- | --- | --- |
| 实习僧 | C | 服务端渲染，`WebFetch` 能读出完整岗位卡片 |
| 应届生求职网 | B 或 A | 列表由 JS 渲染，C 只能读到筛选条件 |
| 牛客校招 | C | 可读，但 `?keyword=` 不生效，须按关键词本地过滤 |

## 3. 硬边界（违反即中止本次搜索）

1. **翻页上限**：单条查询最多 `constraints.max_pages_per_query` 页（默认 3）。不是「尽量多」，是硬上限。
2. **频率**：相邻两次抓取间隔不少于 `search_policy.collect_delay_seconds_min` 秒（默认 2）。不并发、不轮询、不重试轰炸。
3. **遇到以下任一情况立即停止**，不得换选择器、换通道、换关键词绕过：
   - 验证码、滑块、人机校验
   - 登录墙（需要登录才能看更多）
   - 「访问过于频繁」「异常流量」类提示
   - 页面结构与本文件描述的卡片字段完全对不上
4. **绝不调用平台非公开接口**。不许从浏览器开发者工具里抄 API 直接请求 —— 那是绕过前端限制，不是只读浏览。
5. **绝不执行写操作**：不点「立即沟通」「投递」「收藏」「关注」。搜索阶段只有读。
6. **绝不代填登录凭据**。出现登录墙就把控制权交还用户。

## 4. 卡片字段映射

抓到一条岗位卡片，按下表落到 `jobs/raw/` 的字段。**抓不到就留空，由 `normalize_jobs.py` 写入 `missing_info`，绝不猜测补全。**

| raw_jobs 字段 | 从卡片哪里取 | 抓不到时 |
| --- | --- | --- |
| `company` | 公司名 | 留空 → `missing_info: 公司名称缺失` |
| `title` | 岗位名 | 留空 → `missing_info: 岗位名称缺失` |
| `location` | 城市 / 区 | 留空 → `missing_info: 工作地点缺失` |
| `salary` | 日薪 / 月薪 / 面议 | 留空 → 薪资维度给默认分，不按行业均值猜 |
| `url` | 详情页链接 | 留空是**严重问题**：该岗位无法回溯，可信度维度降到底档 |
| `source` | 固定填 `campus_vertical_search` | — |
| `requirements` / `responsibilities` | 卡片上的标签、要求摘要 | 留空，不写「详见原页」这种无效占位 |
| `posted_at` | 发布时间 | 留空 |
| `collected_at` | 抓取当下时间（ISO 8601 +08:00） | 必填 |

**关于 `source` 取值的重要说明**：搜索来的岗位 `source` 填 `campus_vertical_search`，**不加入** `config/settings.json` 的 `trusted_sources`。原因是聚合平台存在转载、过期、信息不全的情况，信息可信度维度理应比官网直招低一档。这是刻意设计，不是缺陷。

因此产生一条实用规则：**同一个岗位若在官网也找到了，以官网那条为主记录**。交由用户在去重报告中选择。

## 5. 落盘规则

- 一次搜索一个文件：`jobs/raw/{platform_id}-{YYYY-MM-DD}.json`，例如 `jobs/raw/shixiseng-2026-10-29.json`。
- 文件结构沿用现有约定：`{schema_version, note, collected_at, jobs: [...]}`。
- **只增不改**：同一天的第二次搜索写 `-2` 后缀（`shixiseng-2026-10-29-2.json`），不覆盖已有文件。
- 文件头 `note` 必须写明：平台、关键词、通道（A/B/C）、页数、抓取时间。
- 抓取失败、空结果也要留痕：写一份 `jobs/raw/{platform_id}-{YYYY-MM-DD}.failed.md`，记录失败原因，不要静默跳过。

## 6. 搜索完成后的必答三问

每次搜索结束，在报告里回答：

1. **这次搜到什么**：几条查询、几个平台、抓到多少岗位、去重后多少。
2. **哪些没搜到 / 搜不到**：哪条查询空结果、哪个平台被拦、哪些字段普遍缺失。
3. **建议下一步**：哪些值得进评分、要不要换关键词、要不要人工补搜某个平台。

## 7. 能力未接入时的降级

- **`browser_exec` 未 verified 且通道 C 也拿不到**：只输出 L1 搜索计划（`search-plan-*.md`），明确告知「这些链接需要你自己点开」，不假装已搜。
- **牛客这类关键词参数不生效的平台**：抓列表后在本地按 `keyword_groups` 过滤，报告中注明「该平台为列表级抓取，非精确搜索」，避免用户误以为已全量覆盖。
- **绝不在能力缺失时凭常识编造岗位**。宁可交出一份空结果 + 失败原因。

## 8. 与其他环节的衔接

```
config/search.json
      │ search_urls.py（L1）
      ▼
jobs/raw/search-plan-{date}.md      ← 用户点开看
      │ Agent 抓取（L2，通道 C/B/A）
      ▼
jobs/raw/{platform}-{date}.json     ← 岗位卡片
      │ normalize_jobs.py（L3）
      ▼
jobs/jobs.normalized.json → score_jobs.py → …
```

搜索只负责把岗位**带进来**，不负责判断好坏。判断由步骤 4 的评分完成，两者不要混在一起 —— 否则「搜到很多」会被误当成「匹配很多」。

## 9. 维护要求

- 平台 URL 参数失效时：改 `config/search.json` 的 `search_url` 与 `verified_at`，**不改脚本**。
- 新增平台时：必须实测一次并把 `params_verified` / `fetch_mode` 填真实值，不许照抄别的平台。
- 排除词调整：改 `config/search.json` 的 `exclude_keywords`。脚本只做子串匹配，不做语义判断。
